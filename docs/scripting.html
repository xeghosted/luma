Scripting

Two ways to write code: a flat .lua file in the game's scripts/ directory, or a resource — a folder with a manifest that can be started, stopped and restarted while the game runs. Start flat; move to a resource when you want lifecycle.

A flat script

Every .lua file in /data/<game>/scripts/ is loaded at boot, in directory order, after natives.lua. There is no manifest and no lifecycle: the file runs once, and whatever it registers keeps running. 

-- /data/gtalua/scripts/hello.lua
local frames = 0

on_tick(function()
    frames = frames + 1
    if frames < 1800 then return end       -- about a minute at 30 fps
    frames = 0

    local ped = GET_PLAYER_PED(-1)
    local c   = GET_ENTITY_COORDS(ped, true)
    log(string.format("ped=%d at %.1f, %.1f, %.1f", ped, c[1], c[2], c[3]))
end)
Register your tick callback unconditionally. Reloading the script directory clears the tick list and then re-runs every file, so a plain on_tick(fn) at the top level is right and cannot accumulate copies. Do not guard it behind a global flag: globals live in the same lua_State and survive the reload, the tick list does not, so the file would skip the registration it believes it already did and leave nothing driving your code at all.

on_tick

on_tick(fn) runs fn every frame, on the game thread. That is what makes drawing and input work: the graphics and control natives are frame-scoped — they contribute to the frame being built right now rather than painting something that stays — so anything that stops calling them every frame simply disappears.

It also means your callback is inside the game's frame. Take too long and the game stutters. A callback that raises is logged once and removed, so it cannot spam the log every frame — which is convenient, and also means a bug can make your script vanish without further comment. Wrap anything risky in pcall.

Calling natives

natives.lua binds every native the build registers under its canonical name. They are ordinary Lua functions; there are no RVAs in script code. 

local ped = GET_PLAYER_PED(-1)                    -- GTA V
local ped = PLAYER_PED_ID()                       -- RDR2
SET_ENTITY_COORDS(ped, x, y, z + 50.0, false, false, false, true)
local speed = GET_ENTITY_SPEED(ped)               -- a float return
local c     = GET_ENTITY_COORDS(ped, true)        -- a Vector3 return -> {x, y, z}

Each binding carries a signature — one character per slot, return type first:

vvoidiintffloat
bboolsstringppointer
3Vector3 — arrives as a Lua table {x, y, z}

Names you will not find

On RDR2, 2,325 of the 7,072 natives have a spelled-out name. The other 4,747 are bound as _0x<16 hex digits>, because no public name exists for them. They are perfectly callable — you just have to know which one you want. GTA V's names are near-complete by comparison.

natives_ready()

On GTA V, 3,674 of 6,485 natives have no static address and are resolved by walking the running game's own table at boot. Those raise if the walk failed. natives_ready() tells you whether that half is live. On RDR2 every address is known before boot, so it is true as soon as the image base resolves. Check it if your script must not half-run: 

if not natives_ready() then return end

Out-parameters and memory

A native with a p slot wants an address to write into. mem_alloc(n) gives you zeroed scratch, capped at 64 KiB. 

local lo, hi = mem_alloc(24), mem_alloc(24)
if lo and hi then
    GET_MODEL_DIMENSIONS(GET_ENTITY_MODEL(ped), lo, hi)
    local a, b = read_vector3(lo), read_vector3(hi)
    log(string.format("model is %.2f m tall", b[3] - a[3]))
end
if lo then mem_free(lo) end
if hi then mem_free(hi) end
Check what mem_alloc gave you. It returns nil when the allocation fails, and the definitions say so, so skipping the check is a type warning in the editor. It is also worth heeding: a native called with a nil address runs on the game thread, where a bad pointer takes the game down instead of raising a Lua error you can read.
A Vector3 out-parameter is 24 bytes, not 12. The game reads and writes x, y and z at an 8-byte stride, not packed. Allocate 24 and use read_vector3, which spells that layout once. Allocating 12 and reading p + 4 as y gives garbage — and it is quiet garbage, which is worse.
mem_alloc(n)Zeroed scratch, ≤ 64 KiB. Returns an address, or nil if the allocation itself failed.
mem_free(p)Release it.
read_mem(p, size)Unsigned integer. size is 1, 2, 4, or 8 (the default).
write_mem(p, v, size)The low size bytes of v.
read_float(p) / write_float(p, v)One 32-bit float.
read_string(p)A NUL-terminated C string. nil only for a null pointer.
read_vector3(p)The 8-byte-stride layout above, as {x, y, z}.
rva(offset)Absolute address of an eboot offset.

Output

log(...) / print(...)To the log file and out to the editor. Every argument is stringified and joined with tabs.
notify(...)The same, plus a PS4 on-screen notification.
Why print does not reach the screen. It used to. One notification per logged line filled a queue that drains slower than a timer-driven script fills it, and the plugin's own load and error messages ended up behind a backlog of coordinates. The screen is now opt-in. notify also logs, so nothing said on screen is lost when the display cuts a long line.

Calling a native the bindings do not name

For a native this build does not name, or a one-off you do not want a permanent binding for: 

local my_native = native(0x9CCAC0, "vffffiiiii")     -- by address
local other     = native_hash(0x897B441FF18ECBBB, "f") -- by 64-bit hash

invoke(0x9CCAC0, {ARG_VOID, ARG_FLOAT, ARG_FLOAT}, 0.5, 0.5)
invoke_hash(0x897B441FF18ECBBB, {ARG_FLOAT})

native and native_hash parse the signature once and hand back a reusable callable — that is exactly what every generated binding is. invoke_raw infers types from the Lua values but always returns a 32-bit int, so a float- or Vector3-returning native needs the explicit form. native_addr(hash) asks the game's table where a hash resolves, which makes it the authority when you are auditing an address.

Script globals

local v = script_global(1574918)
set_script_global(1574918, 1)

GTA V only. On RDR2 the block table has not been located, so both functions raise rather than read and write an address derived from nothing. That is the one capability the two games do not share.

Resources

A resource is a folder under /data/<game>/resources/ with an fxmanifest.lua. It can be started, stopped and restarted while the game runs, and stopping it undoes what it registered — threads, timers, event handlers, commands and exports all come back down with it. 

resources/myscript/
├── fxmanifest.lua
└── client.lua
-- fxmanifest.lua
fx_version 'cerulean'
game 'gta5'

name 'myscript'
author 'you'
version '1.0.0'

client_script 'client.lua'

The manifest is Lua evaluated in a sandbox, under an instruction budget, so a manifest that loops forever fails instead of hanging the game. fx_version, game and games are accepted and ignored — they are there so a FiveM manifest parses unchanged. server_script is warned about and skipped: there is no server on a single-player console.

The resource API

CreateThread(function()
    while true do
        Wait(500)                       -- milliseconds; Wait(0) is "next frame"
        local ped = GET_PLAYER_PED(-1)
        if IS_PED_IN_ANY_VEHICLE(ped, false) then
            SET_VEHICLE_FIXED(GET_VEHICLE_PED_IS_IN(ped, false))
        end
    end
end)

AddEventHandler('onResourceStart', function(name)
    if name == GetCurrentResourceName() then print('up') end
end)

RegisterCommand('heal', function(source, args, raw)
    SET_ENTITY_HEALTH(GET_PLAYER_PED(-1), 200)
end)

exports('where', function()
    local c = GET_ENTITY_COORDS(GET_PLAYER_PED(-1), true)
    return c[1], c[2], c[3]
end)

local x, y, z = exports.myscript:where()
ThreadsCreateThread, CreateThreadNow, Wait, SetTimeout, ClearTimeout — also under Citizen.*
EventsAddEventHandler, RemoveEventHandler, TriggerEvent, RegisterNetEvent
CommandsRegisterCommand
Exportsexports('name', fn) to publish, exports.other:fn() to call
LifecycleStartResource, StopResource, GetResourceState, GetCurrentResourceName
Compatibilityon_tick works inside a resource too — it is an alias that spawns a thread looping on Wait(0), so it is tracked and stopped with the resource like anything else

Starting resources at boot

/data/<game>/autostart.cfg, one resource name per line. Anything not listed sits there until you start it — from the editor, from another resource, or from the console.

Autocomplete

editor/lua-defs/<game>/ holds generated LuaLS definitions for every native plus a hand-written one for the runtime API. Point a .luarc.json at the folder for your game and sumneko.lua will complete every native name and signature. The extension's New Resource command scaffolds this for you.

Do not push a definitions file to the console. A type stub in scripts/ would be loaded and run on every boot from then on. The definitions belong next to the game project, not in the game's data root — the editor refuses to push one for exactly this reason.
