Internals

How one binary serves two games, how a Lua call becomes a RAGE native call, and the two traps that cost the most to find.

Telling the games apart

Luma is one .prx listed under several title ids, so the first thing it must do is work out which game loaded it. Getting that wrong means the wrong address table, which means every native call jumps somewhere arbitrary — so it does not guess. It reads a byte signature at each profile's hook address and checks every candidate, not just until the first hit:

  • No match → it logs the bytes it actually found and stops.
  • Two matches → the fingerprints are not distinguishing, so it refuses rather than picking a game by array order.

Both signatures were checked against both eboots in all four combinations offline. tools/check_detour_target.py re-derives that, and tests/run.sh runs it for each profile on every test run.

The signature does double duty

It is the frame hook's own prologue — deliberately, because those bytes already had to be verified for a second reason (below). Reusing them as the fingerprint means one check covers both questions and there is no second constant to keep in step with the first.

The trap that looked like a clean boot

GoldHEN's Detour relocates nothing. It measures instruction lengths with HDE64, mmaps a stub, memcpys the displaced prologue into it, and writes a 14-byte jump over the original. Nothing rewrites rip-relative operands or relative branches. Any such instruction inside those 14 bytes is silently broken in the copy.

RDR2's PLAYER_PED_ID is the idiomatic hook target and carries mov rax,[rip+0x62dcbbb] at offset 6 — inside the patch. Hooking it produced a boot log that looked completely healthy, followed by a crash. 47% of that build's natives have the same shape, so a hook target cannot be chosen by name.

Luma hooks GET_PLAYER_PED instead — 0xAA9310 on GTA V, 0x21B9140 on RDR2 — whose first 14 bytes are all position-independent. The prologue is checked at install time and the hook refuses if the bytes do not match, so a wrong address fails loudly instead of at some later frame.

Calling a native

RAGE natives all have the same C signature: they take a pointer to a call context and return void. Everything — arguments, return value, vector scratch — lives in that struct. The layout is byte-identical between GTA V and RDR2, which was verified against RDR2's own disassembly rather than assumed:

OffsetField
0x00return pointerwhere the native writes its result
0x08arg count
0x10arg array8 bytes per slot, regardless of type
0x18m_data_counthow many vector slots the native claimed
0x20m_script_vectors4 entries, 8 bytes each — the caller's buffers
0x40m_result_vectors4 entries, 16 bytes each — the scratch the native writes

Those three offsets are static_asserted in src/rage/invoker/invoker.h rather than trusted, and the host test pokes the struct by raw byte offset — the way the game reaches into it — so reordering a field fails the test instead of failing on console.

Why Vector3 is the hard part

A Vector3 return arrives as three separate 8-byte slots: x at +0, y at +8, z at +0x10. Not packed floats.

A Vector3 out-parameter is worse. The native does not write your buffer. It records the address in m_script_vectors, writes its answer into m_result_vectors, and returns — and the caller is expected to copy the results back. Miss that step and every such native appears to work while returning zeroes forever. That is why set_vector_results exists, and why read_vector3 insists on a 24-byte buffer.

m_data_count is written by the game, so it is not trusted: it is clamped to four before being used as a loop bound.

Finding 7,072 natives without a console

The two games could hardly be more different here.

GTA V: a masked table, walked at runtime

The registry at RVA 0x3E0F910 is XOR-masked and only exists in the running process, so Luma walks it at boot, unmasks each node, and then verifies the result before trusting it: it calls GET_HASH_KEY on a known string and compares against the joaat value computed locally. If that check fails, the hash-bound half of the bindings raises instead of dispatching into whatever the walk produced. The walk finds 6,691 entries on the shipping build with 0 rejected, which is what backs the 3,674 hash-bound bindings; the other 2,811 are reached by address and need no walk.

RDR2: registrations in the clear

RDR2's compiler emitted every registration inline and unobfuscated: 

movabs  rcx, 0x4EDE34FBADD967A6      ; the hash        (WAIT)
lea     rdx, [rip + 0x3906ef3]       ; the handler
mov     [r14 + rax*8 + 0x48], rcx    ; node->hashes[i]
mov     [r14 + rax*8 + 8],  rdx      ; node->funcs[i]

tools/extract_registry.py disassembles backwards from the store pair — +0x48 for the hash, +0x08 for the handler — and recovers all 7,072 hash → RVA pairs from eboot.bin alone, in about four seconds. No console, no debugger.

Anchoring on the store rather than on the hash literal is what makes it complete. There are four distinct encodings in the wild, and a scanner looking for movabs misses three of them:

  • movabs + lea — the common case above.
  • The hash folded into the store as an imm32 (TIMESTEP, 0x50597EE2).
  • lea rcx,[r13+disp], deriving a neighbour's hash from a base.
  • Plain register-to-register moves.

tools/gen_natives.py then joins the recovered addresses against names and signatures on the hash, never on position. That matters: joining two ordered lists is how eleven natives once ended up with a neighbour's address and its signature. On a hash join, a name and an address can only meet if they belong to the same native.

RDR2's hashes are version-stable — 98–99% overlap across builds — so a new version moves addresses, not identities.

The control channel

A plain TCP server on the game thread's mailbox: 9615 for GTA V, 9616 for RDR2. Every message is a 12-byte header and an optional payload.

  4   1       op          opcode
  5   1       flags
  6   2       seq         little-endian uint16
  8   4       len         little-endian uint32, payload bytes, ≤ 8 MiB

The opcode table and a set of encoded vectors live in one fixture, tests/protocol_vectors.json, which both sides assert against — the C++ codec and the extension's TypeScript. Renumbering one side alone turns that side red. The extension keeps a vendored copy, so a framing change has to be made in both places or each half only agrees with itself.

Paths

Every path the channel accepts is relative and resolved under the detected game's data root by a guard that rejects traversal. That is what lets one extension serve both games without knowing which one it is talking to: it sends scripts/foo.lua and the plugin decides whether that means /data/gtalua/ or /data/rdr2lua/.

Authentication

Off by default. Write a secret to /data/<game>/token and the channel refuses everything that does not present it. An empty file, or one holding only whitespace, leaves the channel open rather than creating a secret nothing could ever match — an accident that would otherwise lock you out silently.

Without a token, anyone who can reach the port can run arbitrary Lua in the game. That is the same trust level GoldHEN's FTP already grants on the same network. Fine on a home LAN; not fine anywhere else.

The Lua side

One lua_State for everything: flat scripts, resources and the editor console all share it, which is why =menu() in the console can toggle something a script defined. The standard library is trimmed — base, coroutine, table, string, math, utf8, debug — with no io or os.

on_tick callbacks live in a registry array driven once per frame, with per-callback error isolation: one that raises is logged and removed by a swap-remove that re-checks the element it moved into the freed slot, so a second bad callback cannot be skipped by the removal of the first.

Reloading clears that list first. on_tick appends and nothing ever removed an entry, so before runtime_clear_ticks() every reload left a second copy of every callback registered. Two copies are not merely wasteful: both run in the same frame and see the same input, so a script that toggled state on a button press flipped it twice and stopped responding after its first reload — in the push-and-reload loop that is the normal way to work.

Resources are unaffected either way. Their on_tick is a sandbox alias that spawns a scheduler thread and never touches that list, so clearing it takes out exactly the flat scripts the reload is about to re-run.

Testing

Everything below the ORBIS line is plain C++ and Lua and runs on a PC: the native bridge and its marshalling, the wire codec, the path guard, the token policy, the resource model and its scheduler. tests/run.sh also gates the things a unit test cannot see:

  • the committed generated bindings against a fresh regeneration, so the compiler and scripts cannot be handed different addresses;
  • src/script/embedded_lua.h against the .lua files it is generated from — the console runs the header, not the files, and a stale header would leave every Lua suite green while testing code that does not ship;
  • each profile's hook target still being safe to detour;
  • the editor's runtime definitions naming every global the runtime installs;
  • source-level facts about ORBIS-only code no host test can link — that log_sink does not call notify, that the notify sink is installed at all, and that script_reload clears the tick list before reloading.

Each of those gates fails loudly if its own pattern stops matching, rather than passing vacuously. A gate that can quietly stop checking is worse than no gate.
